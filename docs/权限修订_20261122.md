# ColorOS 预设与重启保存权限修订

证据：用户 Downloads/log.txt 中 18:21:01/10/20，DapController 收到 Movie/Music/Dynamic，
随后 persist.vendor.audio.scenario 写入返回 PROP_ERROR_PERMISSION_DENIED。
旧 v1.0.7 和当前 ad9a8e3 规则 catalog 只含 property read，无 property_service set。
本地只读 ColorOS 输入 E:/MIO/17.0.202 中 persist.vendor.audio. 对应 vendor_audio_prop。

2026-11-22 拉取 https://github.com/Pong-Development/hardware_dolby，分支 16，
提交 b2963f7c2c7835389e7c16bdb0946ff9311d20e2。当前 hal_dms_default.te 已明确修复相同场景属性。
latest 原文归档保留该来源；历史有效授权完整保留，增量合入 set_prop。

改动：policy_rules 给 HIDL/AIDL DMS 完整 property socket/connectto/read/set，
扩展数据库的 ioctl/lock/watch/rename/reparent 等权限；policy_sources 按当前 contexts
追加实际音频场景与 Dolby 数据标签，通用类型存在也不漏掉专属标签；旧规则不删。
按用户明确要求 assets/dolby.cil 和模块规则将 hal_dms_default、hal_aidl_dms_default 设 permissive。
不把共享 system_server/音频/App 域设 permissive，不提供普通应用全局放行。

模块新增 storage-access.sh，限定 /data/vendor/dolby、用户0的 org.lunaris.dolby CE/DE目录，
普通文件和目录 777，vendor属主media，App属主保留，restorecon按系统包表恢复MCS。
启动前及首次解锁后各执行一次，安装APK失败前也修复现存App标签与设置文件。
无数据删除/重建、卸载、设置清空及常驻扫描。符号链接不遍历，硬链接文件不chmod/chown。
这解决已存在文件的权限问题；应用后续新建文件可能仍为0600，777不跨越其他App SELinux。

管理器材料：用户提供 LunarisDolby_ColorOS17_3.1.6_Miuix_debug.apk.1，
package org.lunaris.dolby / versionCode 8 / ColorOS17-3.1.6。
它与云端生成器0.2.11 payload中的APK逐字节相同，使用相同现有签名，不重新签管理器。
3.1.7-root-test1（versionCode9）不是本轮选用管理器；较高已安装版本不能无损强行降级，
PackageManager拒绝时保持原包和数据。未执行任何手机安装或重启。

原生 Build共用新属性策略与DMS permissive，但模块的数据权限脚本不写入原生ROM。
未改共享HyperOS工作树/自动化入口、生产ROM或IMG。

回退：生成器本地源码改动可按Git差异精确撤回；已安装模块禁用并完整重启撤销动态策略。
777权限不会随卸载自动收紧；需要按原设备期望模式恢复，保留设置内容。
当前离线测试不能证明对方设备的权限注入成功、Flyme启动或重启保存已修好。
